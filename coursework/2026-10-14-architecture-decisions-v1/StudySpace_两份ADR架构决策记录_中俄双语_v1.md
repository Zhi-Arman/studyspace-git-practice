| 背景<br>需求 约束 驱动因素 / Контекст<br>требования ограничения силы | 四人课程团队需协作交付查询、校内审核和预约；系统要求三语界面、统一 API、可重复构建及服务端权限和事务校验，开发效率与运行复杂度影响选择。<br>Команда из четырёх участников создаёт поиск, проверку вуза и бронирование; нужны три языка, единый API, воспроизводимая сборка, серверные права и транзакции при приемлемой сложности разработки и запуска.<br><br>需求 / Требования<br>SP-C-005, SP-C-006, SP-NFR-001, SP-IF-001, SP-FR-004, SP-NFR-004 | 开发环境需便于本地启动；预约要求阻止同学生或同座位的时段重叠，并保持事务原子性、UTC 时间语义和迁移后数据关联，目标数据库需独立验证。<br>Нужен простой локальный запуск; бронь требует запрета пересечений студента и места, атомарности, семантики UTC и сохранения связей при миграции, целевая БД проверяется отдельно.<br><br>需求 / Требования<br>SP-C-005, SP-C-001, SP-C-002, SP-NFR-004, SP-NFR-005, SP-TR-001, SP-DR-003 |
| 决策 / Решение | 沿用 React／TypeScript 浏览器客户端和 FastAPI 后端，经 JSON API 通信；后端按认证、审核、资源、预约和统计划分内部模块，保持单体部署。<br>Сохранить браузерный клиент React/TypeScript и сервер FastAPI с JSON API; внутри сервера выделить аутентификацию, проверку, ресурсы, бронирование и статистику при монолитном развёртывании.<br><br>Pydantic 校验输入，同步 SQLAlchemy 访问数据库；权限和预约冲突由服务端事务最终校验，uv/npm 锁定依赖。<br>Pydantic проверяет входы, синхронный SQLAlchemy обращается к БД; права и конфликты окончательно проверяются серверной транзакцией, зависимости фиксируются uv/npm. | 开发默认 SQLite，目标部署候选为 PostgreSQL，通过 SQLAlchemy 和 DATABASE_URL 统一访问与配置；首个业务实体前引入 Alembic。<br>В разработке использовать SQLite, кандидат для целевого развёртывания PostgreSQL; SQLAlchemy и DATABASE_URL задают общий доступ и конфигурацию, Alembic вводится до первой бизнес-сущности.<br><br>在两库分别验证迁移、回滚和预约并发；使用 [start,end) 区间，同一学生可有多条非重叠预约，创建与取消在服务端事务内完成。<br>На обеих БД отдельно проверить миграцию, откат и конкурентное бронирование; интервалы [start,end), несколько непересекающихся броней студента допустимы, создание и отмена выполняются серверной транзакцией. |
| 后果<br>优点与缺点 / Последствия<br>плюсы и минусы | 优点 运行单元较少，业务模块可共享事务，便于四人团队开发、测试和交接。<br>Плюсы Меньше единиц запуска, общая транзакция для бизнес-модулей, проще разработка, проверка и передача небольшой командой.<br><br>缺点 前后端需同步 API 契约；后端故障可影响全部业务，模块间依赖需控制，独立扩缩容能力受限。<br>Минусы Нужно согласовывать API клиента и сервера; сбой сервера затрагивает весь бизнес, зависимости модулей требуют контроля, отдельное масштабирование ограничено. | 优点 简化本地开发，同时保留目标数据库迁移路径和统一数据访问层。<br>Плюсы Простой локальный запуск с сохранением пути к целевой БД и общего слоя доступа к данным.<br><br>缺点 需维护两库的迁移与测试；ORM 不替代事务、约束和时区验证，上线前还需备份恢复演练。<br>Минусы Нужны миграции и проверки обеих БД; ORM не заменяет проверку транзакций, ограничений и времени, до запуска требуется восстановление из резервной копии. |
| 替代方案及放弃原因 / Альтернативы и причины отказа | 微服务 可独立部署和扩缩容，但增加接口、部署及跨服务一致性成本，本次课程范围不采纳。<br>Микросервисы дают отдельное развёртывание и масштабирование, но усложняют интерфейсы, запуск и согласованность между сервисами; для текущего курса не выбраны.<br><br>单一全栈框架 可减少前后端衔接工作，但需改造已建 React/FastAPI 骨架，本次保留现有技术基础。<br>Один full-stack фреймворк уменьшает связующую работу, но требует переделки каркаса React/FastAPI; в этом выпуске сохранена имеющаяся основа. | 全程仅 SQLite 配置简单，但不覆盖已选择的 PostgreSQL 目标环境及其并发、迁移验证，因此不作为唯一方案。<br>Только SQLite упрощает настройку, но не покрывает выбранную целевую среду PostgreSQL и её проверки конкуренции и миграции; не выбран единственным вариантом.<br><br>全程仅 PostgreSQL 可减少两库差异，但为每位成员的基础本地运行增加数据库服务依赖，本阶段保留 SQLite 开发入口。<br>Только PostgreSQL сокращает различия БД, но добавляет зависимость от сервиса БД для базового локального запуска каждого участника; на этом этапе сохранён вход через SQLite. |

## 复查条件 Условия пересмотра

学校核验来源 OPEN-003、课程条件 OPEN-008 和部署环境 OPEN-010 明确，或业务模型、负载及模块边界变化时复查；迁移、并发、恢复和业务验收分别保存实际证据。
Пересмотреть после определения источника вуза OPEN-003, условий курса OPEN-008 и среды OPEN-010 либо изменения модели, нагрузки и границ модулей; миграция, конкуренция, восстановление и бизнес-приёмка требуют отдельных свидетельств.
