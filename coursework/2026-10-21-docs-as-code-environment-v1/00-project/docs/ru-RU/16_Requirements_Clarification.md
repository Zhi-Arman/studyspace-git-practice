## 2 Конкретные правила и приоритеты

Бронируется Seat; Room содержит кампус, корпус, этаж, имя, CLASSROOM/STUDY_ROOM, часы и состояние. Seat уникален по room_id+seat_code и имеет состояние; ёмкость выводится из включённых мест. Бронирование помещения не обходит контроль места, графическая карта не обязательна, исторические ресурсы мягко отключаются.

Моменты хранятся UTC, деловой день/отображение — Asia/Shanghai; начало/конец на целом или получасе с нулевыми секундами и микросекундами. Начало строго позже фактической проверки после блокировок; минимум30 минут, максимум24ч. Даты — сегодня...сегодня+6 по моменту проверки. Окно дня[D00:00,(D+1)00:00), конец допускает совпадение с правой границей без времени следующего дня.

Обычно ежедневно, включая праздники без исключений,08:00–22:00; явное исключение администратора приоритетно. Поэтому фактический обычный максимум14ч; предел24ч не обещает такую доступность каждому ресурсу. Только будущий день с00:00–24:00 даёт допустимый пример24ч. Часы, один деловой день, окно дат и длительность проверяются совместно.

Для одногоSeat и одногоuser_id неотменённые записи проверяются existing.start<new.end иnew.start<existing.end; соседние допустимы. Один студент не имеет пересекающихся интервалов даже на разныхSeat, но может иметь несколько непересекающихся одного или разных будущих дней, без глобального лимита незавершённых. Одна запись одноSeat с прежними ограничениями времени/часов/дат. Отмена освобождает только её интервал, сохраняя другие; для сменыSeat в пересекающемся интервале сначала отмена.

Студент отменяет при now<start после блокировок, с начала — администратор с причиной. Повтор идемпотентен без повторного счёта и события аудита. Отключение ресурса/места, сокращение часов и отключение аккаунта атомарно отменяют затронутые незавершённые записи; включение их не восстанавливает. SQLite начинает BEGIN IMMEDIATE; PostgreSQL создаёт с User→Room→Seat и фактическим now после блокировок. Закрытие берёт Room→Seats по ID без обратных User; User защищает проверку интервалов студента, не суммарного количества; конфликт ищется по записям без кэша лимита. Timeout блокировки отличается от установленного конфликта; не вся ошибка БД означает409.

Роль, активность и проверка независимы. Бронирует ENABLED+STUDENT+VERIFIED; PENDING входит для чтения. Ручная проверка использует настоящий источник вуза, необходимые номер/имя и проверяющего/момент/состояние/ссылку без изображения; изображения не хранятся, неизвестный источник не даёт автоматического успеха. Номер уникален среди сохраняющих идентичность аккаунтов; изменение идентификаторов возвращает PENDING и отменяет незавершённые записи. Первый администратор создаётся явной интерактивной CLI без пароля в аргументах, исходного пароля и повышения роли при регистрации.

Бронирования хранятся180 дней от завершения: canceled_at при отмене, иначеend; аудит —180 дней отevent_at. Текущая проверка действующего аккаунта не исчезает при удалении старого события. Отключение минимум30 дней без незавершённых записей — лишь ранний порог. Необратимая очистка идентификаторов: max(отключение+30 дней, истечение всех связанных идентифицирующих записей); до этого связь ограниченно сохраняется, полной анонимности на30-й день нет. Логи не копируют номер/имя и не содержат пароль, token или изображения. Ежедневных резервных копий семь; восстановление начинает с очистки до открытия сервиса. Это учебная политика без заявления правового соответствия.

Все показатели группируются по дате бронированияD и одномуas_of: created_count —created_at≤as_of, canceled_count —canceled_at≤as_of, not_ended_count —не отменено кas_of иend>as_of. Будущие входят в незавершённые; это не фактическая занятость, посещаемость или загрузка. Очищенные данные недоступны, а не вымышленный0. Базовая статистика вMVP; напоминания, QR, нарушения и загрузка — будущий объём.
