## 1 Область и источники

[Контракт OpenAPI 3.1.0](../api/openapi.yaml) (SS-API-04 0.1.0) оформляет три выбранные бизнес-точки по учебному примеру стиля RoomBook. Китайские и русские описания находятся в одном YAML; этот документ и китайская пара описывают одно решение. Источники — схемы US-002, US-004 и задания SS-API-01/02/03 о точках, операциях и данных. Для полного MVP нужны другие API; здесь только два учебных сценария.

Приложение остаётся каркасом 0.1.0; бизнес-API не реализован, тесты NOT_RUN. Рабочий `/api/v1/openapi.json` генерируется FastAPI и описывает только существующие health/ready. Статический бизнес-контракт хранится отдельно и не доказывает наличие работающих точек.

## 2 Операции и ответы

| Операция | Метод и путь | operationId | Успех | 4xx |
| --- | --- | --- | --- | --- |
| OP-01 | `POST /api/v1/bookings` | `createBooking` | 201 | 401, 403, 409, 422 |
| OP-02 | `GET /api/v1/identity-reviews/pending` | `getPendingIdentityReview` | 200 | 401, 403, 404, 422 |
| OP-03 | `POST /api/v1/identity-reviews` | `saveIdentityReviewDecision` | 200 | 401, 403, 409, 422 |

Оба POST задают `requestBody.required=true` и `application/json`; GET использует обязательный параметр запроса `user_id`. Запросы и ответы ссылаются на схемы через `$ref`. Все 4xx возвращают `Error{code,message}`, 401 также задаёт `WWW-Authenticate: Bearer`. Только установленный конфликт даёт 409; тайм-аут блокировки и иные ошибки БД не считаются бизнес-конфликтом автоматически.

## 3 Схемы, обязательность и ограничения

| ID задания | Схема | Назначение |
| --- | --- | --- |
| DS-01 | `BookingCreateRequest` | seat_id, D, start, end обязательны; user_id клиента не принимается |
| DS-02 | `BookingCreatedResponse` | booking_id, seat_id, start, end обязательны |
| DS-03 | `PendingReviewQuery` | user_id обязателен; набор параметров GET, не тело |
| DS-04 | `PendingReviewResponse` | user_id, student_no, full_name, status, revision обязательны |
| DS-05 | `IdentityReviewDecisionRequest` | user_id, decision, source_type, source_ref, revision обязательны |
| DS-06 | `IdentityReviewDecisionResponse` | user_id, status обязательны |
| DS-07 | `Error` | code, message обязательны |

Все объекты имеют `additionalProperties=false`. ID и revision длиной 1–128, student_no1–64, full_name1–200, source_type1–64, source_ref1–256, message1–500. Это технические предложения, соответствие формату номера вуза пока не заявляется. ID и revision — непрозрачные строки без предопределения UUID, целого числа или JWT. D имеет формат date, границы — date-time с поясом; revision возвращается без изменений.

Ожидающий status только PENDING; решение и сохранённый status — VERIFIED или REJECTED. code принимает AUTH_REQUIRED, FORBIDDEN, REVIEW_NOT_FOUND, VALIDATION_ERROR, SOURCE_UNVERIFIABLE, STUDENT_OVERLAP, SEAT_OVERLAP, STALE_REVIEW. Все схемы и ошибки содержат вымышленные примеры структуры; SOURCE_TYPE_TBD/REFERENCE_TBD не проходят реальную проверку источника.

## 4 Защита, время и транзакции

Все операции задают `security: [{bearerAuth: []}]`. Bearer — предлагаемый транспорт учётных данных сессии; выдача, отзыв, хранение, срок и политика паролей рассматриваются до реализации, JWT не предопределён. Сервер на каждом запросе проверяет текущую личность, активность и права. Бронь создаёт только активный студент VERIFIED; читать и сохранять проверки может администратор с соответствующим правом.

Действуют DEC-016 и разрешённые правила времени: Asia/Shanghai, сегодня...сегодня+6 после блокировок, шаг/минимум 30 мин, максимум 24 ч, обычно 08:00–22:00. start строго позже момента проверки и относится к D; end может равняться 00:00 D+1. Соседние [start,end) допустимы, пересечения студента или места запрещены, несколько непересекающихся разрешены. Допуск, ресурс, время, конфликт, запись и минимальный аудит проверяются/фиксируются в одной транзакции; JSON Schema проверяет только статический формат.

Признанный вузом источник OPEN-003 ещё не определён. Достоверное совпадение позволяет VERIFIED, несоответствие — REJECTED. Непроверяемый источник даёт 422 с сохранением PENDING, устаревший снимок —409 STALE_REVIEW. Аудит не копирует номер, имя и изображения документов.

## 5 Трассируемость и синхронизация

OP-01 связан с US-002, SP-FR-007, SP-FR-008, SP-FR-009, SP-NFR-004 и DEC-016. OP-02 связан с US-004, SP-FR-004, SP-FR-022, SP-DR-001. OP-03 дополнительно связан с SP-IF-002 и OPEN-003. Поля YAML `x-operation-id`, `x-coursework-id`, `x-traceability` сохраняют связи.

Задание 1 задаёт точки, задание 2 — операции, коды и роли, задание 3 — семь схем и примеры. `scripts/check_api_contract.py` сверяет пути, коды, имена схем, обязательные поля, примеры и параметры времени проекта с YAML. После изменения синхронизируются обе языковые инструкции и источники заданий, затем пересобираются затронутые Word. Официальные требования и 38 бизнес-кейсов сохраняют PROPOSED/NOT_RUN по исходному реестру.

## 6 Проверка и свидетельства

Среда — локальная macOS, проектная `backend/.venv` и зафиксированные зависимости разработки. Команды выполняются из корня:

```bash
backend/.venv/bin/python scripts/check_api_contract.py --report artifacts/api-contract-validation.json
python3 scripts/check_docs.py
python3 scripts/generate_registers.py --check
```

Проверяются спецификация OpenAPI, локальные ссылки, все примеры Schema/ответов/параметров, отклонение пропущенных полей, лишнего user_id, неверного времени, длинного ID и неверного решения, а также согласованность заданий. Бизнес-сервис не запускается; конкуренция, права, реальный источник и приёмка этим не доказываются. Фактический результат сохраняется в указанном отчёте; бизнес-тесты NOT_RUN.

Фактически 2026-10-16: пройдены 110 статических проверок контракта (17 примеров,6 отклонений),20 серверных и 19 клиентских тестов, клиентские lint/типы/сборка. Обе обновлённые Word-таблицы проверены визуально на одной странице. Общая проверка остановилась на 719 замечаниях Ruff в 9 прежних учебных скриптах; новый скрипт прошёл lint/формат. Локальный отчёт: `artifacts/api-contract-completion.json`, список прежних замечаний: `artifacts/api-contract-existing-lint.json`.
